# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## O que é

Um bot em Python (baseado em Playwright) que monitora novos projetos no [99Freelas](https://www.99freelas.com.br) (marketplace brasileiro de freelancers), filtra os projetos com base num perfil configurado pelo usuário e envia propostas automaticamente usando um template fixo — sem revisão manual por envio. Feito para rodar continuamente (24/7) via Docker num servidor. Todos os comentários, logs e docs do código estão em português (pt-BR); mantenha essa convenção ao editar este repositório.

## Setup e comandos

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
playwright install chromium

cp .env.example .env               # preencha as credenciais do 99Freelas (opcional, ver abaixo)
cp config.example.yaml config.yaml # preencha os critérios do perfil

python bot/import_cookies.py caminho/para/cookies_exportados.json  # sessão via cookies (ver Arquitetura abaixo — é o caminho que funciona)
python bot/dry_run.py              # modo simulação: preenche mas NUNCA envia de verdade (seguro pra testar)
python bot/main.py                 # roda o bot de verdade (a partir da raiz do repo, não de dentro de bot/)
```

Rode primeiro localmente com `HEADLESS=false` no `.env` para ver o navegador e confirmar que login/envio de proposta funcionam de verdade antes de rodar sem supervisão.

Deploy via Docker:
```bash
docker compose up -d --build
docker compose logs -f
```

Não há suíte de testes, linter ou build configurados neste repo — não há nada a rodar além do próprio bot.

## Arquitetura

O bot roda uma única sessão de navegador Playwright de longa duração num loop `while True` (`bot/main.py`), dormindo um intervalo aleatório entre ciclos. Cada módulo em `bot/` tem uma responsabilidade única:

- `main.py` — ponto de entrada; carrega config/env, autentica (`open_authenticated_page`) e chama `run_cycle` repetidamente. Envolve cada ciclo em try/except para que uma falha nunca derrube o processo 24/7. O `sys.path` é ajustado no topo do arquivo para permitir rodar diretamente com `python bot/main.py`.
- `manual_login.py` — script standalone (`python bot/manual_login.py`) pra login manual numa janela visível controlada pelo Playwright; salva a sessão (cookies) em `data/auth_state.json`. **Confirmado que não funciona nesta conta**: o formulário de login usa Cloudflare Turnstile, que bloqueia o login (via Google OU via email/senha) sempre que detecta navegador controlado por automação — mesmo com janela visível e interação manual. Mantido no repo como referência, mas o caminho que funciona de fato é `import_cookies.py`.
- `import_cookies.py` — **caminho de autenticação que efetivamente funciona**: o usuário loga no navegador do dia a dia (fora do bot, onde o Turnstile passa normalmente), exporta os cookies de `99freelas.com.br` (ex: extensão Cookie-Editor, "Export as JSON") e roda `python bot/import_cookies.py caminho/para/export.json`. O script filtra só os cookies do domínio certo, converte pro formato de `storage_state` do Playwright e salva em `data/auth_state.json`.
- `dry_run.py` — modo de simulação: mesmo loop de `main.py`, mas chama `submitter.submit_proposal(..., dry_run=True)`, que preenche os campos e NUNCA clica no botão final de envio. Usa rastreio próprio (`data/dry_run_seen.json`), separado de `data/applied_jobs.json` — simular um projeto aqui nunca impede o bot real de candidatar-se a ele depois. Criado pra validar o pipeline inteiro (scraping, filtro, descrição completa, IA, notificação) em tempo real enquanto o plano pago do usuário está inativo.
- `scraper.py` — abre a página de listagem de projetos (`site_selectors.PROJECTS_LIST_URL`, filtro salvo "dev" do usuário no próprio site) e extrai dados estruturados de cada card: id (via `data-id`, com fallback pra regex na URL), título, url, categoria (ver `_extract_category`), descrição, `posted_minutes_ago`. `budget` vem sempre `None` — a listagem não mostra orçamento (ver nota abaixo).
- `filter.py` — `is_match(project, config)` decide se um projeto é aderente ao perfil (idade máxima `max_project_age_minutes`, palavras-chave de inclusão/exclusão, categorias, faixa de orçamento), retornando `(bool, motivo)` para log. Listas/campos vazios/`null` na config significam "não filtra por isso".
- `proposal.py` — `build_proposal(project, config, lowest_bid=None, full_description=None)` monta oferta/prazo/texto. A oferta pode vir do orçamento do cliente, de um valor fixo, ou (estratégia `menor_proposta`) de um percentual (`undercut_percent`) abaixo do menor valor já proposto por outro freelancer — com fallback pro orçamento do cliente se ainda não houver concorrência. O texto vem de `ai_writer.generate_proposal_text` quando `proposal.texto_modo == "ia"` e há `full_description`; se a IA falhar/for rejeitada ou o modo for `"fixo"`, usa o template de `proposal.texto` em `config.yaml`.
- `ai_writer.py` — gera o texto da proposta via IA (Anthropic ou Gemini, configurável em `proposal.ia_provider`/`ia_model`) a partir da descrição completa do projeto. Regras (sem contato/valor/prazo, sem jargão técnico/nomes de tecnologia — cliente é leigo) são reforçadas em dois níveis: instrução no prompt E um filtro automático (`_safety_violation`: regex de e-mail/URL/telefone/"R$"/tamanho máximo) que rejeita e cai pro template fixo se o texto gerado violar alguma regra mesmo assim.
- `notifier.py` — `notify_proposal_result(project, proposal, status, detail)` manda uma notificação Telegram (`TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` no `.env`) a cada tentativa de envio (sucesso ou falha), chamada de dentro de `submitter._finish`. Falha sempre silenciosamente (só loga warning) — notificação nunca pode derrubar o ciclo do bot. Não é chamada para projetos ignorados pelo filtro (isso seria ruído demais).
- `submitter.py` — login por email/senha (fallback, ver `main.py` — confirmado que falha por causa do Turnstile, ver abaixo) e envio de proposta via interações com a página no Playwright: checa "já enviado" (por presença, nunca clique — ver nota abaixo), lê a descrição completa da página do projeto (`_read_full_description`, antes de sair dela), clica em "Enviar proposta" (navega pra `/project/bid/...`, precisa `expect_navigation`), lê o campo de menor proposta concorrente (`_read_lowest_bid`, ainda não disponível — plano do usuário inativo), monta a proposta com `proposal.build_proposal`, preenche e confirma o envio (que redireciona de volta pra página do projeto, também com `expect_navigation`). Todo retorno passa por `_finish()`, que dispara a notificação antes de retornar — se adicionar um novo caminho de saída na função, usar `_finish()` também, não `return` direto.
- `storage.py` — persiste os IDs de projetos já candidatados e a contagem diária de envios em `data/applied_jobs.json`, usando escrita atômica (`os.replace` a partir de um `.tmp`) e um lock de thread. É isso que evita candidaturas duplicadas entre reinícios e garante a cota diária.
- `site_selectors.py` — **todos** os seletores CSS/XPath usados em qualquer parte do bot ficam aqui, e só aqui. Quando o HTML do site mudar ou um seletor precisar de ajuste, este é o único arquivo a mexer. **Não renomeie de volta para `selectors.py`** — esse nome colide com o módulo `selectors` da stdlib do Python e quebra o `asyncio`/`subprocess` (usado pelo Playwright) quando o script é rodado como `python bot/algo.py`, porque o Python coloca a pasta do script no início do `sys.path`.
- `utils.py` — `parse_currency`/`format_currency_br` (conversão R$ ↔ float, compartilhadas entre `scraper.py`, `submitter.py` e `proposal.py`), `minutes_since_epoch_ms`/`parse_relative_time_minutes` (idade do projeto a partir do atributo `cp-datetime` ou, em fallback, do texto "há X minutos/horas").
- `logger_setup.py` — `get_logger(name)` retorna um logger que escreve tanto no console quanto num arquivo rotativo (`logs/bot.log`).

Fluxo de dados por ciclo (`run_cycle` em `main.py`): faz scraping da listagem → ignora IDs já candidatados → para cada projeto novo, roda `filter.is_match` → se aderente, `submitter.submit_proposal` (que internamente lê a descrição completa e a menor oferta concorrente, monta a proposta com `proposal.build_proposal`, e notifica o resultado via `notifier`) → `storage.register_application` independente do resultado (sucesso, falha e ignorado são todos registrados, então nada fica sendo retentado infinitamente).

## Contexto importante para mudanças

- **Seletores de login, listagem e formulário de proposta já foram validados** contra HTML real — não são mais chutes. A lista completa de campos validados vive só em `bot/site_selectors.py` (não duplicar aqui; ela tem comentários explicando cada um). **Ainda pendentes**: `PROPOSAL_LOWEST_BID` e onde fica o orçamento do cliente na página do projeto — bloqueados porque o plano pago do usuário ainda não está ativo (sem isso essas seções da página não aparecem). Retomar quando o usuário mandar o HTML.
- **Bug real corrigido**: o marcador de "proposta já enviada" inclui `#btnCancelarProposta` (um link que CANCELA a proposta se clicado). O código original usava `page.click()` pra checar esse marcador — clicar nele cancelaria propostas já enviadas. Corrigido pra `page.query_selector()` (checagem de presença, nunca clique). Se algum dia reintroduzir uma checagem "existe X na página", pensar sempre se o elemento é seguro de interagir antes de usar `.click()` como forma de "testar presença".
- **"Enviar proposta" e o botão de confirmar envio são navegações de página real** (`/project/bid/...` e volta pra página do projeto), não revelam formulário/toast na mesma página — por isso ambos os cliques em `submitter.py` usam `page.expect_navigation(wait_until="networkidle")`. Se replicar esse padrão de clique+espera em outro lugar, não esquecer o `expect_navigation`.
- **O campo de oferta (`#oferta`) espera formato brasileiro** (`"1234,56"`, vírgula decimal, `type="tel"` com máscara) — sempre usar `utils.format_currency_br()` ao preencher, nunca `str(float)` puro (isso já foi um bug real, corrigido).
- **A listagem de projetos não mostra orçamento** — confirmado no HTML real (só categoria, nível, data, descrição, contagem de propostas/interessados, cliente). `project["budget"]` vem sempre `None` do `scraper.py`. Isso importa para `proposal.py`: se não houver orçamento do cliente E não houver proposta concorrente pra basear o undercut (`menor_proposta`) — hoje sempre o caso, já que ambos dependem do plano pago ainda inativo — a oferta cai pra `oferta_fixa` ou `0`. **Não ativar o bot em produção até `oferta_fixa` ter um valor de segurança no `config.yaml`, ou até o plano estar ativo e esses campos serem validados** — senão o bot pode enviar proposta de R$0,00.
- **Login automatizado é bloqueado por Cloudflare Turnstile**: confirmado testando as duas formas (clique automatizado no Google e preenchimento automatizado de email/senha via `submitter.login`, seletores já validados: `#email`, `#senha`, `#btnEfetuarLogin`) — o Turnstile no formulário rejeita ambas com "token de acesso inválido" por detectar automação. Não tentar contornar isso (stealth plugins, resolvedores de captcha etc.) — é a proteção do próprio site funcionando como esperado. O caminho funcional é `import_cookies.py` (cookies exportados do navegador comum do usuário, já logado). `data/auth_state.json` gerado por ele é reaproveitado por `main.py` via `open_authenticated_page`. `submitter.login` (email/senha) só roda como fallback se esse arquivo não existir, mas está confirmado que vai falhar por causa do Turnstile. Quando a sessão salva expira, o bot loga um erro e para — é esperado que o usuário refaça a importação de cookies, não algo pra "corrigir" automaticamente.
- **`config.yaml`, `.env` e `data/auth_state.json` são gitignored e específicos do usuário/sessão**; só os `.example` ficam commitados. Nunca commite credenciais reais, cookies de sessão ou um `config.yaml` preenchido.
- **Cota de propostas**: `MONTHLY_PROPOSAL_QUOTA` no `.env` (240, correspondente às conexões do plano do usuário) é dividido pelos dias do mês corrente em `main.daily_quota()`, recalculado a cada ciclo — não é um número fixo por dia. Isso, junto com os delays aleatórios entre ciclos/propostas (`CHECK_INTERVAL_MIN/MAX_SECONDS`, além do sleep de 5–15s entre propostas dentro de um mesmo ciclo), existe especificamente para não gastar a cota mensal de uma vez e evitar parecer spam para a plataforma — preserve esse comportamento ao refatorar o loop de ciclos.
- **Conexões do plano**: cada proposta enviada consome uma "conexão" do plano 99Freelas do usuário (visível no dashboard em "Minhas conexões"). O plano Gratuito dá só ~10/mês; o valor de `MONTHLY_PROPOSAL_QUOTA=240` no `.env` assume que o usuário está num plano pago com 240 conexões/mês — se o plano mudar, esse valor precisa ser atualizado junto, senão o bot vai tentar enviar mais propostas do que há conexões disponíveis e as excedentes vão falhar.
- **Modelos "thinking" do Gemini (ex: `gemini-3.6-flash`) consomem `max_output_tokens` com raciocínio interno antes do texto final** — sem `thinking_config=ThinkingConfig(thinking_budget=0)` em `ai_writer._generate_with_gemini`, o texto sai cortado na metade (confirmado testando: `thoughts_token_count` alto, resposta truncada). Não remover esse `thinking_budget=0` sem motivo forte.
- **Chaves de API vazam e são detectadas**: já aconteceu nessa sessão — o Google rejeitou uma `GEMINI_API_KEY` com "Your API key was reported as leaked" mesmo sem ela nunca ter sido commitada (`.env` é gitignored). Se isso acontecer de novo, a chave precisa ser revogada e trocada por uma nova em https://aistudio.google.com/apikey — não adianta tentar reusar a mesma.
- **Bug real corrigido em `is_logged_in()`**: usava `page.wait_for_selector(..., timeout=3000)` sem especificar `state`, que por padrão exige o elemento **visível**. O seletor `a[href^='/user/']` provavelmente bate primeiro com uma versão escondida (menu mobile/responsivo) antes da visível, fazendo a checagem falhar (timeout) mesmo com sessão 100% válida — reproduzido de forma consistente (`query_selector` achava o elemento, `wait_for_selector` não). Corrigido com `state="attached"` (só checa presença no DOM). Se `is_logged_in()` voltar a reportar falso negativo, suspeitar de visibilidade/duplicação do seletor antes de assumir que a sessão expirou.
- Como tudo roda totalmente automatizado, sem revisão humana do texto da proposta antes do envio, seja conservador ao alterar o comportamento de `filter.py`, `proposal.py` ou `submitter.py` — um bug aqui causa diretamente envios de proposta indesejados no mundo real.
