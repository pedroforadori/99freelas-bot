# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## O que é

Um bot em Python (baseado em Playwright) que monitora novos projetos no [99Freelas](https://www.99freelas.com.br) (marketplace brasileiro de freelancers), filtra os projetos com base num perfil configurado pelo usuário, monta a proposta (texto via IA, oferta/prazo calculados ou sugeridos por IA) e manda pro Telegram pra aprovação humana antes de qualquer envio real — **não há mais envio 100% automático** (havia antes desta sessão; substituído por um portão de aprovação, ver `approvals.py`/`notifier.py` na Arquitetura abaixo). Feito para rodar continuamente (24/7) via Docker num servidor. Todos os comentários, logs e docs do código estão em português (pt-BR); mantenha essa convenção ao editar este repositório.

## Setup e comandos

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
playwright install chromium

cp .env.example .env               # preencha as credenciais do 99Freelas (opcional, ver abaixo)
cp config.example.yaml config.yaml # preencha os critérios do perfil

python bot/import_cookies.py caminho/para/cookies_exportados.json  # sessão via cookies (ver Arquitetura abaixo — é o caminho que funciona)
python bot/dry_run.py              # modo simulação: preenche mas NUNCA envia de verdade (seguro pra testar)
python bot/main.py                 # roda o bot de verdade (a partir da raiz do repo, não de dentro de bot/)
```

Rode primeiro localmente com `HEADLESS=false` no `.env` para ver o navegador e confirmar que login/envio de proposta funcionam de verdade antes de rodar sem supervisão.

Deploy via Docker:
```bash
docker compose up -d --build
docker compose logs -f
```

**Testes (pytest) — rode antes de reiniciar o bot** (`pip install -r requirements-dev.txt`, depois `python -m pytest`). Nada toca rede, Playwright ou o `data/` real: `tests/conftest.py` isola `data/` num `tmp_path`, troca o Telegram por um fake que grava cada chamada (`requests.post`) e congela a data. `tests/snapshots/` guarda o texto/teclado exato de cada mensagem do Telegram — se um snapshot quebrar, é mudança visível pro usuário; só regrave (`UPDATE_SNAPSHOTS=1 python -m pytest`) quando a mudança for intencional, nunca pra "consertar" um refactor. O fixture `api` do conftest é o único ponto dos testes que sabe onde cada função mora. Não há linter nem build.

## Arquitetura

O bot roda uma única sessão de navegador Playwright de longa duração num loop `while True` (`bot/main.py`), dormindo um intervalo aleatório entre ciclos. Tudo que é específico de uma **fonte de vagas** (99Freelas, GitHub) vive em `bot/sources/<fonte>/`, atrás da interface `JobSource` (`bot/sources/base.py`) — o núcleo (loop, portão de aprovação, roteamento do Telegram) nunca pergunta "qual fonte é essa?". Ver "Como adicionar uma nova fonte de vagas" abaixo. Cada módulo tem uma responsabilidade única:

- `sources/base.py` — o contrato `JobSource` (Strategy + Template Method). A fonte implementa: `run_cycle(config)` (varredura — só pede aprovação, nunca envia), `render_approval(project, proposal)` → (texto, teclado), `deliver(entry)` (envio de verdade), `on_delivered`/`on_rejected` (registro), e opcionalmente `is_enabled`, `start(browser)` (ex: autenticar), `tick(config)` (trabalho do loop interno), `owns_id`, `editable_fields` (tupla de `EditableField`: código de 1 char no `callback_data`, botão, prompt, `parse`, `apply`), `callback_routes()` (botões próprios, prefixo → `CallbackRoute(arity, handler)`), `handle_message` (mensagem solta no chat) e `retry_preparation`. Partes comuns já prontas na base: `queue_for_approval` (grava `project["source"] = name`, manda a mensagem, `approvals.add_pending`; com `require_message_id=True` não enfileira se o Telegram falhar), `resolve_approval` (rejeitado → `on_rejected` + rótulo final + `resolve`; aprovado → `already_delivered`? → `deliver` → rótulo final → `on_delivered` → `resolve` ou `mark_failed`), `edit_buttons`, `notify` (log de atividade com a tag da fonte), `MAX_QUEUED_PER_CYCLE`.
- `sources/registry.py` — `ALL_SOURCES` (o ÚNICO lugar que lista as fontes; a primeira é a padrão), `enabled_sources(config)`, `source_of(project)` (pelo campo `"source"`; ausente = 99Freelas, compatível com entradas antigas de `pending_approvals.json`), `source_for_id(id)` (por `owns_id`, quando não há entrada em approvals). Fica fora de `sources/__init__.py` (que é vazio, assim como os `__init__` das subpastas) pra evitar import circular: `submitter.py`/`messages.py` importam `sources/freelas99/views.py`, e um `__init__` que importasse as fontes puxaria `submitter.py` de volta.
- `telegram_api.py` — transporte puro da Bot API (`send_message`, `call`, `send_with_keyboard`, `edit_text`, `edit_reply_markup`, `answer_callback`, `static_label_keyboard`, offset do `getUpdates` em `data/telegram_offset.json`, `esc`). Nunca levanta exceção. **Não renomear pra `telegram.py`** (colidiria com pacote de terceiros quando roda `python bot/x.py` — mesmo problema do `selectors.py`).
- `telegram_dispatcher.py` — `TelegramDispatcher(ALL_SOURCES, config).poll()`: short-poll (`getUpdates` com `timeout=0`, nunca long-poll — bloquearia a única thread) e roteamento. Fluxos genéricos que servem qualquer fonte: `approve:`/`reject:` (grava a decisão em `approvals` ANTES de tudo, depois troca o teclado por "⏳ Processando..."), `editf:<code>:<id>` + reply (campo vem de `source.field(code)`; prompt com `force_reply`, correlação da resposta por `approvals.find_by_prompt_message_id`, valor inválido mantém o `pending_edit`, sucesso edita o texto da mensagem original via `render_approval`), `retry:<id>` (entrada `"failed"` → volta pra `"approved"`; senão `source_for_id(id).retry_preparation`). Prefixos próprios de cada fonte vêm de `callback_routes()`; prefixo duplicado → `ValueError` na inicialização. Callback desconhecido/aridade errada/`noop` → só responde o clique. Mensagem solta → a primeira fonte cujo `handle_message` retorne True. Nunca toca o Playwright.

- `main.py` — ponto de entrada, só orquestra: carrega config/env, abre o Chromium só se alguma fonte ativa tiver `needs_browser`, chama `start(browser)` de cada fonte ativa (False → encerra, ex: sessão do 99Freelas expirada) e roda um loop **aninhado**: o externo chama `run_cycle` de cada fonte ativa no ritmo de `CHECK_INTERVAL_MIN/MAX_SECONDS`, cada uma protegida por `_CycleGuard` (try/except com contador de falhas consecutivas POR fonte — notifica `cycle_error`/`cycle_recovered` com a tag da fonte só na 1ª falha da sequência e na recuperação; uma fonte falhando não afeta a outra); o interno, a cada `APPROVAL_POLL_INTERVAL_SECONDS` (default 20s), chama `dispatcher.poll()` + `process_pending_approvals()` (cada decisão vai pra `source_of(project).resolve_approval` — usa `ALL_SOURCES`, então item já na fila continua resolvível mesmo com a fonte desligada) + `tick(config)` de cada fonte ativa — é isso que permite reagir rápido a um clique sem esperar a próxima varredura. Erros do loop interno ficam só no log. Aprovação envia mesmo acima da cota diária (ver "Cota de propostas"). Registra `SIGTERM` (`docker compose stop`/`restart`/`down`) como `KeyboardInterrupt`, mesmo caminho de parada "limpa" (com notificação) do Ctrl+C. O `sys.path` é ajustado no topo pra rodar com `python bot/main.py`.
- `sources/freelas99/` — fonte 99Freelas. `source.py` (`Freelas99Source`): `start` autentica via `auth.open_authenticated_page` (sessão de `data/auth_state.json`, ver `import_cookies.py`) e guarda a `Page`; `run_cycle` = `connections.refresh` → (se `aguardar_media`) `_recheck_awaiting_average` → scraping → `filter.is_match` → `submitter.prepare_proposal` → pedido de aprovação + `register_application(..., "pending_approval")`; `tick` = `process_manual_projects` (links colados) + `messages.check_and_notify` na cadência própria `MESSAGES_POLL_INTERVAL_SECONDS` (default 60s — cada checagem navega até `/dashboard`); `deliver` = `submitter.finalize_submission`; campos editáveis oferta (`o`) e prazo (`p`, ambos marcam `ajustado_manualmente`); botões próprios `retryia:` (texto via IA de novo) e `link:<p|r|f>:` (menu de link colado); `handle_message` = link de projeto colado no chat; `retry_preparation` = reenfileira o link da mensagem de falha em `manual_queue`. `views.py`: todos os textos/teclados do 99Freelas (`approval_text`, `approval_keyboard`, `notify_proposal_result` — chamado por `submitter._finish` —, `notify_new_messages` — chamado por `messages.py` —, `notify_manual_project_failed`, `send_link_menu`, `_origem_line`, `_propostas_hoje_line`, `_conexoes_usadas_line` etc.). Não importa `source.py` (evita ciclo). `auth.py`: `open_authenticated_page` (também usado por `dry_run.py`).
- `approvals.py` — fila de propostas prontas aguardando aprovação humana, persistida em `data/pending_approvals.json` (mesmo padrão atômico de `storage.py`). `add_pending(project, proposal, message_id)` enfileira; `record_decision(project_id, action)` grava `"approved"`/`"rejected"` — chamado pelo `TelegramDispatcher` IMEDIATAMENTE ao receber o clique no Telegram, ANTES de qualquer coisa no Playwright, o que garante que uma aprovação nunca se perde mesmo se o processo cair logo depois (a decisão já está em disco; `main.process_pending_approvals` a retoma no próximo tick). Idempotente: gravar a mesma decisão de novo (duplo-clique, redelivery do Telegram) é um no-op seguro. `update_proposal(project_id, proposal)` sobrescreve a oferta/prazo pendente (usado pela edição por texto livre, ver `TelegramDispatcher._on_edit_reply`) — recusa (retorna `False`) se já houver decisão gravada, mesma proteção de `record_decision`, pra nunca reabrir uma proposta que já está sendo (ou já foi) processada. `set_pending_edit(project_id, field, prompt_message_id)`/`find_by_prompt_message_id(prompt_message_id)`/`clear_pending_edit(project_id)` dão suporte a esse fluxo: quando o usuário clica "✏️ Editar ...", `TelegramDispatcher._on_edit_request` manda uma mensagem nova com `force_reply` e grava `{field, prompt_message_id}` na entrada; quando a resposta chega, `find_by_prompt_message_id` (varre as entradas pendentes) traduz o `message_id` do prompt de volta em `(project_id, field)`, já que o Telegram só devolve isso em `reply_to_message`, nunca o `project_id` diretamente. `get_decided_unresolved()`/`resolve(project_id)` completam o ciclo de vida.
- `manual_login.py` — script standalone (`python bot/manual_login.py`) pra login manual numa janela visível controlada pelo Playwright; salva a sessão (cookies) em `data/auth_state.json`. **Confirmado que não funciona nesta conta**: o formulário de login usa Cloudflare Turnstile, que bloqueia o login (via Google OU via email/senha) sempre que detecta navegador controlado por automação — mesmo com janela visível e interação manual. Mantido no repo como referência, mas o caminho que funciona de fato é `import_cookies.py`.
- `import_cookies.py` — **caminho de autenticação que efetivamente funciona**: o usuário loga no navegador do dia a dia (fora do bot, onde o Turnstile passa normalmente), exporta os cookies de `99freelas.com.br` (ex: extensão Cookie-Editor, "Export as JSON") e roda `python bot/import_cookies.py caminho/para/export.json`. O script filtra só os cookies do domínio certo, converte pro formato de `storage_state` do Playwright e salva em `data/auth_state.json`.
- `dry_run.py` — modo de simulação: mesmo loop de `main.py`, mas chama `submitter.submit_proposal(..., dry_run=True)`, que preenche os campos e NUNCA clica no botão final de envio. Usa rastreio próprio (`data/dry_run_seen.json`), separado de `data/applied_jobs.json` — simular um projeto aqui nunca impede o bot real de candidatar-se a ele depois. Criado pra validar o pipeline inteiro (scraping, filtro, descrição completa, IA, notificação) em tempo real enquanto o plano pago do usuário está inativo.
- `scraper.py` — abre a página de listagem de projetos (`site_selectors.PROJECTS_LIST_URL`, filtro salvo "dev" do usuário no próprio site) e extrai dados estruturados de cada card: id (via `data-id`, com fallback pra regex na URL), título, url, categoria (ver `_extract_category`), descrição, `posted_minutes_ago`. `budget` vem sempre `None` — a listagem não mostra orçamento (ver nota abaixo).
- `filter.py` — `is_match(project, config)` decide se um projeto é aderente ao perfil (idade máxima `max_project_age_minutes`, palavras-chave de inclusão/exclusão, categorias, faixa de orçamento), retornando `(bool, motivo)` para log. Listas/campos vazios/`null` na config significam "não filtra por isso".
- `proposal.py` — `build_proposal(project, config, lowest_bid=None, full_description=None)` monta oferta/prazo/texto, ou retorna **`None`** no único caso em que não há nenhum dado pra basear um preço (ver próximo parágrafo) — quem chama (`submitter.prepare_proposal`) trata isso como falha de preparo, nunca monta proposta com oferta zerada. A oferta pode vir do orçamento do cliente, de um valor fixo, ou (estratégia `menor_proposta`) de um percentual (`undercut_percent`) abaixo do valor médio das propostas concorrentes já enviadas. **Quando não há nem `lowest_bid` nem orçamento do cliente** (comum em projetos recém-publicados — ver `PROPOSAL_LOWEST_BID` abaixo), em vez de cair direto pra `oferta_fixa`/0, chama `ai_writer.suggest_price_and_deadline` pra pedir um valor/prazo coerente à IA (decisão explícita do usuário: sem piso fixo configurado — a IA julga o valor por projeto, buscando o mais baixo possível pra maximizar aceitação; o portão de aprovação humana, não um piso hard-coded, é quem garante que nada com valor ruim seja realmente enviado). O texto vem de `ai_writer.generate_proposal_text` quando `proposal.texto_modo == "ia"` e há `full_description`; se a IA falhar/for rejeitada ou o modo for `"fixo"`, usa o template de `proposal.texto` em `config.yaml`. `_build_texto` retorna também `texto_ia_falhou` (bool) — True só no caso específico de `texto_modo == "ia"` COM `full_description` disponível mas a geração falhando/sendo rejeitada (ou seja, a IA foi chamada e falhou, não simplesmente "não foi chamada") — vira o campo `resultado["texto_ia_falhou"]` de `build_proposal`, que `notifier.py` usa pra mostrar um aviso e o botão "🔄 Tentar gerar via IA novamente" na mensagem de aprovação (ver bullet de `notifier.py` e "Retry de texto via IA" abaixo). `build_proposal` também devolve `origem_valor` (`"ia"` | `"menor_proposta"` | `"orcamento_cliente"` | `"fixo"`, ver `ORIGEM_LABELS`) indicando de qual dos quatro ramos veio a oferta/prazo — existe especificamente pra `notifier.py` mostrar essa origem na mensagem do Telegram, já que "IA sugeriu" e "baseado na média de propostas concorrentes" têm níveis de confiança bem diferentes na hora de aprovar. **Desconto competitivo sobre a sugestão da IA** (`_aplicar_desconto_competitivo`, 2026-09-17): confirmado em produção que a IA tende a sugerir um preço de mercado "real" bem acima do que costuma ganhar no 99Freelas (duas propostas reais saíram ~2x o valor que se mostrou competitivo) — por experiência do usuário no site, cliente geralmente fecha com o freelancer mais barato. Paliativo aplicado só no ramo `origem == "ia"`: arredonda a sugestão pra baixo no milhar mais próximo e desconta mais `proposal.ia_desconto_milhar` reais (`config.yaml`, default 1000 — ex: sugestão R$2400 → oferta R$1000; R$3300 → R$2000), nunca abaixo de `proposal.ia_preco_minimo` (default 150), e não mexe em sugestões < R$1000 (já consideradas baixas). Ainda não validado com dados reais — os dois parâmetros existem especificamente pra serem ajustados conforme o resultado das próximas propostas aprovadas. Quando o desconto muda o valor, o dict retornado ganha `oferta_sugerida_ia` (valor bruto da IA, antes do desconto) — `notifier._origem_line` mostra os dois lado a lado na mensagem do Telegram pra facilitar essa calibração. **Nota fixa opcional** (`proposal.nota_extra`, 2026-09-22): texto anexado (com uma linha em branco antes) ao final do texto da proposta, INDEPENDENTE da origem (IA ou template fixo) — usado pra uma alegação factual ("estou começando no 99Freelas, mas tenho portfólio") que o usuário quis manter sempre com a mesma redação exata, nunca parafraseada pela IA a cada geração. Entra em `build_proposal` logo após `_build_texto`, ANTES de `check_text_safety`, então continua coberta pela mesma rede de segurança (nunca escapa da checagem por vir "depois"). `null`/vazio não anexa nada.
- `ai_writer.py` — duas funções que chamam IA (Anthropic ou Gemini, configurável em `proposal.ia_provider`/`ia_model`, provider genérico `_generate_with_anthropic`/`_generate_with_gemini` aceita um `system_prompt` diferente pra cada uso): `generate_proposal_text` gera o texto da proposta a partir da descrição completa do projeto — regras (sem contato/valor/prazo, sem jargão técnico/nomes de tecnologia — cliente é leigo) reforçadas em dois níveis: instrução no prompt E `check_text_safety` (função pública — não é mais `_safety_violation` — porque `proposal.py` também usa ela, ver nota abaixo; regex de e-mail/URL/telefone/"R$"/tamanho máximo). `suggest_price_and_deadline` pede um valor/prazo em JSON estrito (`{"oferta": ..., "prazo_dias": ...}`, parseado com `json.loads` em try/except — mesma filosofia de nunca confiar só no modelo, agora validação de schema+faixa de sanidade ampla em vez de regex) quando não há dado de preço concorrente — ver `proposal.py`.
- `notifier.py` — só as notificações comuns a todas as fontes, falhando sempre em silêncio (notificação nunca pode derrubar o ciclo): `notify_activity(text, tag="")` (log de atividade, desliga com `ACTIVITY_LOG_TELEGRAM=false`), `TelegramErrorHandler`/`install_error_forwarding` (WARNING/ERROR de qualquer módulo vira mensagem, com dedupe de 60s), `notify_bot_status(event, detail, simulated)` (monitoramento de **ciclo de vida** — só em transições: `started`, `stopped`, `stopped_error`, `auth_failed`, `cycle_error`, `cycle_recovered`; rodando normal não gera mensagem; `simulated=True` do `dry_run.py` prefixa `[DRY RUN]`), `send_approval_message(text, keyboard)` e `finalize_approval_message(message_id, approved, detail)` (troca só o TECLADO da mensagem original pelo rótulo final — o texto completo fica no histórico do chat; falha de envio aparece como "❌ Rejeitada — <motivo>", comportamento herdado). NÃO importa `bot.sources`. As linhas "Hoje: X/Y" e "Conexões usadas: X/Y" (em `sources/freelas99/views.py`) somam +1 na proposta atual quando o envio foi real e bem-sucedido — ver nota "Contador 'Conexões usadas...'" abaixo. A linha "Origem do valor/prazo" (`_origem_line`) é omitida se a proposta não tiver `origem_valor` (entradas antigas) e ganha "· ajustado manualmente" depois de uma edição.
  **Fluxo de aprovação (99Freelas)**: a mensagem traz descrição, texto, oferta e prazo — sem truncar o texto da proposta, truncando só a descrição pro limite de 4096 chars. Teclado (`views.approval_keyboard`): linha de edição (`edit_buttons` → `editf:o:<id>`/`editf:p:<id>`), opcionalmente "🔄 Tentar gerar texto via IA novamente" (`retryia:<id>`, só quando `proposal["texto_ia_falhou"]`) e "✅ Aprovar"/"❌ Rejeitar" (`approve:<id>`/`reject:<id>`, limite de 64 bytes do `callback_data` — só o id cabe). Os fluxos de clique/edição/retry são os genéricos do `telegram_dispatcher.py`; o retry via IA (`Freelas99Source._on_retry_ia_text`) chama `ai_writer.generate_proposal_text` de novo com a `full_description` já salva na proposta (sem Playwright) — por isso o dispatcher repassa `config` no `Callback`; em sucesso troca o texto, zera `texto_ia_falhou` e edita a mensagem (some o botão); em falha só um toast.
- `connections.py` — `refresh(page)` navega pra `site_selectors.DASHBOARD_URL` e extrai por regex (no `inner_text()` da página, não há seletor CSS único e estável nesse bloco) o saldo real de conexões: `plano_restantes`/`plano_total` (ex: "240 conexões restantes de um total de 240"), `disponiveis`, `nao_expiraveis` e a data de renovação. Salva em `data/connections.json` (mesmo padrão de escrita atômica de `storage.py`), junto com `baseline_sent_today` (snapshot de `storage.proposals_sent_today()` no momento do refresh). Chamado uma vez por ciclo em `Freelas99Source.run_cycle`/`dry_run.run_cycle`, nunca a cada proposta — `sources/freelas99/views.py` lê o cache (`read_cached()`) sem precisar de acesso à `Page`. Se o parse falhar ou a navegação der erro, loga warning e devolve o último cache válido (nunca derruba o ciclo).
- `messages.py` — mesmo molde de `connections.py`, mas pra avisar sobre respostas de clientes: `refresh(page)` navega pra `site_selectors.DASHBOARD_URL` (mesma URL de `connections.py` — o badge de mensagens fica no header, presente em qualquer página autenticada, então não precisou de uma URL própria de mensagens) e lê o contador de não lidas via `query_selector` num elemento isolado e estável (`MESSAGES_BADGE_CONTAINER`/`MESSAGES_BADGE_VALUE`, confirmados contra HTML real fornecido pelo usuário — diferente de `connections.py`, aqui dá pra usar seletor CSS em vez de regex sobre texto solto). A classe `"show"` no container só aparece quando há mensagens não lidas — sem ela, o contador é tratado como 0 mesmo que o `<span>` interno ainda tenha um valor antigo. Salva em `data/messages_state.json` (mesmo padrão atômico). `check_and_notify(page)` é a função chamada pelo loop (não `refresh` diretamente): lê o cache ANTES de atualizar, chama `refresh(page)`, e só dispara `views.notify_new_messages(novo, anterior)` (`sources/freelas99/views.py`) quando o contador **aumentou** — uma queda (usuário leu as mensagens fora do bot) ou igualdade não notifica nada, decisão explícita do usuário pra evitar ruído. Existe porque a notificação nativa do 99Freelas é lenta/não confiável — ver bullet "Badge de mensagens" abaixo pro que ainda falta validar.
- `manual_queue.py` — **projeto enviado por link (2026-09-23)**: o usuário cola o link de um projeto (`/project/...` ou `/project/bid/...`) no chat do bot principal; `Freelas99Source.handle_message` aceita só mensagens do próprio `TELEGRAM_CHAT_ID`, extrai id/slug e responde com um menu (`views.send_link_menu`) — "📝 Preparar proposta" enfileira em `data/manual_queue.json` (sem tocar o Playwright); "💬 Respondeu"/"🏆 Fechou" marcam o resultado (ver bullet "Estilo do texto sorteado" abaixo). `Freelas99Source.process_manual_projects` (no `tick`, mesma cadência das aprovações) consome a fila: `prepare_proposal` → pedido de aprovação, igual a `run_cycle`, mas **sem `filter.is_match`** (decisão do usuário: se mandou o link, quer propor) e mesmo que o projeto já tenha sido ignorado/rejeitado antes. O título vem de `submitter._read_project_title` (`site_selectors.PROJECT_PAGE_TITLE` = `span.nome-projeto`, validado contra HTML real, sem o "(+ detalhes)" do filho; se ausente, slug humanizado). Falha avisa via `views.notify_manual_project_failed` e não sobrescreve registro anterior em `applied_jobs.json` (ex: `"sent"`); item sai da fila mesmo em exceção, pra nunca ficar retentando.

Se `dry_run=True`, preenche mas não clica no botão final — usado por `bot/dry_run.py`.
  - `submit_proposal(page, project, config, dry_run=False)` — wrapper fino: `prepare_proposal` seguido de `finalize_submission`. É o que `dry_run.py` chama; o bot real (`main.py`) usa as duas metades separadamente, com o portão de aprovação do Telegram entre elas.
  Todo retorno de `finalize_submission` passa por `_finish()`, que dispara `views.notify_proposal_result` (`sources/freelas99/views.py`) antes de retornar — se adicionar um novo caminho de saída nela, usar `_finish()` também, não `return` direto. `prepare_proposal` NÃO chama `_finish()` (não é uma notificação de resultado final) — `main.run_cycle` notifica diretamente quando o preparo falha.
- **Portfólio (2026-09-21) — captura + aprovação no Telegram, SEM upload no site (decisão explícita do usuário; ele sobe à mão)** — `python bot/portfolio.py <url...> | --app-store URL --play-store URL | --file x.yaml [--variant N]`. Captura as imagens (`portfolio_capture.py`), gera título (≤50)/descrição (≤400) via `ai_writer.generate_portfolio_text` (validados por `check_portfolio_text`, além do prompt), deixa em `data/portfolio/.pendentes/<Nome da empresa>/` (imagens + `texto.txt`; nome via `portfolio_capture.company_name`: `og:site_name`, senão domínio, senão nome do app na loja) e manda pro Telegram (`portfolio_review.py`) as imagens COMO DOCUMENTO (foto é recomprimida) + título/descrição em `<code>`. Com `PORTFOLIO_TELEGRAM_BOT_TOKEN` há botões ✅ Aprovar (move pra `data/portfolio/<Nome>/`) / 🔁 Refazer capturas (próximo `variant`, só sites, mantém o texto) / ❌ Reprovar (apaga), e o próprio comando fica esperando os cliques (long-poll) até decidir tudo; sem o token, sem botões (vai direto pra `data/portfolio/<Nome>/`). **Por que um SEGUNDO bot do Telegram:** ler cliques é `getUpdates` e o offset confirma updates GLOBALMENTE por bot — ler o bot principal aqui descartaria cliques de aprovação de propostas, e dois processos no mesmo bot se atropelam. **Não fazer polling com `TELEGRAM_BOT_TOKEN` neste fluxo.** Independente do bot principal (não usa a sessão do 99Freelas). `portfolio_capture.py`: site = 3 screenshots desktop 1440x960 (3:2, proporção que o site recomenda) + 2 mobile emulado, capa = hero desktop, ordem desktop/mobile/desktop/desktop/mobile; apps = screenshots oficiais (App Store via API pública do iTunes, Play Store via `google-play-scraper`; com as duas lojas: 3 iOS + 2 Android). Limite do 99Freelas = 5 imagens/trabalho. **Histórico:** houve uma versão que publicava sozinha em `/portfolio/edit` (aprovação no bot principal), removida — se voltar: o site tem CSP sem `unsafe-eval`, então `page.wait_for_function` do Playwright falha lá (usar polling em Python); o formulário é um modal (`li.btn-abrir-modal-trabalho`, `#titulo`, `#descricao`, `input.file-upload` com `multiple`, `a.btn-adicionar-editar-trabalho`).
- `storage.py` — persiste os IDs de projetos já candidatados e a contagem diária de envios em `data/applied_jobs.json`, usando escrita atômica (`os.replace` a partir de um `.tmp`) e um lock de thread. É isso que evita candidaturas duplicadas entre reinícios e garante a cota diária. `status` inclui `"sent"` | `"failed"` | `"skipped_duplicate"` | `"pending_approval"` (aguardando decisão no Telegram — já conta como "candidatado" pra `already_applied`, então não é reavaliado de novo enquanto espera) | `"rejected_by_user"`.
- `site_selectors.py` — **todos** os seletores CSS/XPath usados em qualquer parte do bot ficam aqui, e só aqui. Quando o HTML do site mudar ou um seletor precisar de ajuste, este é o único arquivo a mexer. **Não renomeie de volta para `selectors.py`** — esse nome colide com o módulo `selectors` da stdlib do Python e quebra o `asyncio`/`subprocess` (usado pelo Playwright) quando o script é rodado como `python bot/algo.py`, porque o Python coloca a pasta do script no início do `sys.path`.
- `utils.py` — `parse_currency`/`format_currency_br` (conversão R$ ↔ float, compartilhadas entre `scraper.py`, `submitter.py` e `proposal.py`), `minutes_since_epoch_ms`/`parse_relative_time_minutes` (idade do projeto a partir do atributo `cp-datetime` ou, em fallback, do texto "há X minutos/horas"), `daily_quota(monthly_quota)` (divide a cota mensal pelos dias do mês corrente — vive aqui, não em `main.py`, especificamente pra `sources/freelas99/views.py` poder importar sem criar ciclo de import).
- `logger_setup.py` — `get_logger(name)` retorna um logger que escreve tanto no console quanto num arquivo rotativo (`logs/bot.log`).

Fluxo de dados: `main` chama `run_cycle` de cada fonte ativa (ritmo `CHECK_INTERVAL_*`). No 99Freelas: scraping da listagem → ignora IDs já candidatados (inclui `"pending_approval"`) → `filter.is_match` → `submitter.prepare_proposal` (monta, sem enviar) → em sucesso, `queue_for_approval` (Telegram + `approvals.add_pending`) + `storage.register_application(..., "pending_approval")`; em falha de preparo, notifica e registra `"failed"` direto. No GitHub: issues novas → `build_email` → `queue_for_approval` + registro em `github_jobs.json`. Separadamente, no loop interno (ritmo `APPROVAL_POLL_INTERVAL_SECONDS`), o `TelegramDispatcher` grava cliques/edições e `process_pending_approvals` entrega cada decisão pra fonte dona (`resolve_approval`): `"approved"` → `deliver` (proposta real no 99Freelas / e-mail SMTP no GitHub) → registro `"sent"`/`"email_sent"` ou `"failed"` (mantido em approvals pro "🔄 Tentar de novo"); `"rejected"` → `"rejected_by_user"`, sem enviar nada.

## Como adicionar uma nova fonte de vagas

1. Crie `bot/sources/<nome>/` com `__init__.py` vazio, `views.py` (textos/teclados do Telegram, com `TAG = "<b>[Nome]</b>"`, escapando com `esc` tudo que vier de fora) e `source.py` com uma subclasse de `JobSource` (`bot/sources/base.py`): `name`, `tag`, `run_cycle`, `render_approval`, `deliver`, `on_delivered`, `on_rejected`. Se ela tem um cliente de API/scraper próprio, ponha em `client.py` no mesmo pacote.
2. Implemente o que precisar dos opcionais: `is_enabled(config)` (leia uma seção própria do `config.yaml` e documente em `config.example.yaml`), `owns_id` (use um prefixo de id único, ex: `gh-`; ids nunca podem conter `:`, e o `callback_data` inteiro tem limite de 64 bytes), `editable_fields`, `callback_routes` (prefixo novo, sem colidir com `approve`/`reject`/`editf`/`retry`/`retryia`/`link`), `start`/`needs_browser`, `tick`, `handle_message`, `retry_preparation`, `already_delivered` (se `deliver` não for idempotente), `require_message_id`.
3. Registre uma instância em `ALL_SOURCES` (`bot/sources/registry.py`). Nada em `main.py`, `telegram_dispatcher.py` ou `notifier.py` deve precisar mudar — se precisar, a abstração está vazando; ajuste `base.py` em vez de por um `if` por fonte.
4. Registro de resultados: se o envio dessa fonte não gasta conexão do 99Freelas, use um arquivo próprio em `data/` (como `github_jobs.json`) e NUNCA `applied_jobs.json` (o status `"sent"` lá soma na cota diária e no `report.py`). Adicione o arquivo ao `.gitignore` e ao fixture `isolated` de `tests/conftest.py`.
5. Testes: siga `tests/test_sources_registry.py` (fonte fictícia de ponta a ponta) e adicione snapshots das mensagens novas em `tests/test_approval_rendering.py`; ajuste `test_toda_fonte_registrada_e_completa`.
