# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## O que é

Um bot em Python (baseado em Playwright) que monitora novos projetos no [99Freelas](https://www.99freelas.com.br) (marketplace brasileiro de freelancers), filtra os projetos com base num perfil configurado pelo usuário, monta a proposta (texto via IA, oferta/prazo calculados ou sugeridos por IA) e manda pro Telegram pra aprovação humana antes de qualquer envio real — **não há mais envio 100% automático** (havia antes desta sessão; substituído por um portão de aprovação, ver `approvals.py`/`notifier.py` na Arquitetura abaixo). Feito para rodar continuamente (24/7) via Docker num servidor. Todos os comentários, logs e docs do código estão em português (pt-BR); mantenha essa convenção ao editar este repositório.

## Setup e comandos

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
playwright install chromium

cp .env.example .env               # preencha as credenciais do 99Freelas (opcional, ver abaixo)
cp config.example.yaml config.yaml # preencha os critérios do perfil

python bot/import_cookies.py caminho/para/cookies_exportados.json  # sessão via cookies (ver Arquitetura abaixo — é o caminho que funciona)
python bot/dry_run.py              # modo simulação: preenche mas NUNCA envia de verdade (seguro pra testar)
python bot/main.py                 # roda o bot de verdade (a partir da raiz do repo, não de dentro de bot/)
```

Rode primeiro localmente com `HEADLESS=false` no `.env` para ver o navegador e confirmar que login/envio de proposta funcionam de verdade antes de rodar sem supervisão.

Deploy via Docker:
```bash
docker compose up -d --build
docker compose logs -f
```

Não há suíte de testes, linter ou build configurados neste repo — não há nada a rodar além do próprio bot.

## Arquitetura

O bot roda uma única sessão de navegador Playwright de longa duração num loop `while True` (`bot/main.py`), dormindo um intervalo aleatório entre ciclos. Cada módulo em `bot/` tem uma responsabilidade única:

- `main.py` — ponto de entrada; carrega config/env, autentica (`open_authenticated_page`) e roda um loop **aninhado**: o loop externo chama `run_cycle` (varredura — nunca envia nada, só prepara e enfileira aprovações) no ritmo de `CHECK_INTERVAL_MIN/MAX_SECONDS`; entre uma chamada de `run_cycle` e a próxima, um loop interno chama `notifier.poll_decisions()` + `process_pending_approvals` a cada `APPROVAL_POLL_INTERVAL_SECONDS` (bem mais curto, default 20s) — é isso que permite reagir rápido a um clique de aprovação sem esperar o próximo ciclo de scraping inteiro. `process_pending_approvals` é quem de fato usa o Playwright pra enviar (`submitter.finalize_submission`) quando `approvals.get_decided_unresolved()` traz uma decisão `"approved"` (rechecando a cota diária nesse momento — enfileirar não consome cota, só o envio real consome) ou marca como `"rejected_by_user"` sem tocar o Playwright. Envolve `run_cycle` em try/except pra nunca derrubar o processo 24/7 — notifica (`notifier.notify_bot_status`) na 1ª falha de uma sequência e quando o ciclo volta ao normal (não a cada repetição). Erros do loop de polling de aprovação ficam só no log (categoria de falha diferente, não soma no mesmo contador). Registra `SIGTERM` (enviado por `docker compose stop`/`restart`/`down`) como `KeyboardInterrupt`, reaproveitando o mesmo caminho de parada "limpa" (com notificação) do Ctrl+C. O `sys.path` é ajustado no topo do arquivo para permitir rodar diretamente com `python bot/main.py`.
- `approvals.py` — fila de propostas prontas aguardando aprovação humana, persistida em `data/pending_approvals.json` (mesmo padrão atômico de `storage.py`). `add_pending(project, proposal, message_id)` enfileira; `record_decision(project_id, action)` grava `"approved"`/`"rejected"` — chamado de dentro de `notifier.poll_decisions()` IMEDIATAMENTE ao receber o clique no Telegram, ANTES de qualquer coisa no Playwright, o que garante que uma aprovação nunca se perde mesmo se o processo cair logo depois (a decisão já está em disco; `process_pending_approvals` a retoma no próximo ciclo). Idempotente: gravar a mesma decisão de novo (duplo-clique, redelivery do Telegram) é um no-op seguro. `update_proposal(project_id, proposal)` sobrescreve a oferta/prazo pendente (usado pelos botões de ajuste, ver `notifier._handle_adjust`) — recusa (retorna `False`) se já houver decisão gravada, mesma proteção de `record_decision`, pra nunca reabrir uma proposta que já está sendo (ou já foi) processada. `get_decided_unresolved()`/`resolve(project_id)` completam o ciclo de vida.
- `manual_login.py` — script standalone (`python bot/manual_login.py`) pra login manual numa janela visível controlada pelo Playwright; salva a sessão (cookies) em `data/auth_state.json`. **Confirmado que não funciona nesta conta**: o formulário de login usa Cloudflare Turnstile, que bloqueia o login (via Google OU via email/senha) sempre que detecta navegador controlado por automação — mesmo com janela visível e interação manual. Mantido no repo como referência, mas o caminho que funciona de fato é `import_cookies.py`.
- `import_cookies.py` — **caminho de autenticação que efetivamente funciona**: o usuário loga no navegador do dia a dia (fora do bot, onde o Turnstile passa normalmente), exporta os cookies de `99freelas.com.br` (ex: extensão Cookie-Editor, "Export as JSON") e roda `python bot/import_cookies.py caminho/para/export.json`. O script filtra só os cookies do domínio certo, converte pro formato de `storage_state` do Playwright e salva em `data/auth_state.json`.
- `dry_run.py` — modo de simulação: mesmo loop de `main.py`, mas chama `submitter.submit_proposal(..., dry_run=True)`, que preenche os campos e NUNCA clica no botão final de envio. Usa rastreio próprio (`data/dry_run_seen.json`), separado de `data/applied_jobs.json` — simular um projeto aqui nunca impede o bot real de candidatar-se a ele depois. Criado pra validar o pipeline inteiro (scraping, filtro, descrição completa, IA, notificação) em tempo real enquanto o plano pago do usuário está inativo.
- `scraper.py` — abre a página de listagem de projetos (`site_selectors.PROJECTS_LIST_URL`, filtro salvo "dev" do usuário no próprio site) e extrai dados estruturados de cada card: id (via `data-id`, com fallback pra regex na URL), título, url, categoria (ver `_extract_category`), descrição, `posted_minutes_ago`. `budget` vem sempre `None` — a listagem não mostra orçamento (ver nota abaixo).
- `filter.py` — `is_match(project, config)` decide se um projeto é aderente ao perfil (idade máxima `max_project_age_minutes`, palavras-chave de inclusão/exclusão, categorias, faixa de orçamento), retornando `(bool, motivo)` para log. Listas/campos vazios/`null` na config significam "não filtra por isso".
- `proposal.py` — `build_proposal(project, config, lowest_bid=None, full_description=None)` monta oferta/prazo/texto, ou retorna **`None`** no único caso em que não há nenhum dado pra basear um preço (ver próximo parágrafo) — quem chama (`submitter.prepare_proposal`) trata isso como falha de preparo, nunca monta proposta com oferta zerada. A oferta pode vir do orçamento do cliente, de um valor fixo, ou (estratégia `menor_proposta`) de um percentual (`undercut_percent`) abaixo do valor médio das propostas concorrentes já enviadas. **Quando não há nem `lowest_bid` nem orçamento do cliente** (comum em projetos recém-publicados — ver `PROPOSAL_LOWEST_BID` abaixo), em vez de cair direto pra `oferta_fixa`/0, chama `ai_writer.suggest_price_and_deadline` pra pedir um valor/prazo coerente à IA (decisão explícita do usuário: sem piso fixo configurado — a IA julga o valor por projeto, buscando o mais baixo possível pra maximizar aceitação; o portão de aprovação humana, não um piso hard-coded, é quem garante que nada com valor ruim seja realmente enviado). O texto vem de `ai_writer.generate_proposal_text` quando `proposal.texto_modo == "ia"` e há `full_description`; se a IA falhar/for rejeitada ou o modo for `"fixo"`, usa o template de `proposal.texto` em `config.yaml`. `build_proposal` também devolve `origem_valor` (`"ia"` | `"menor_proposta"` | `"orcamento_cliente"` | `"fixo"`, ver `ORIGEM_LABELS`) indicando de qual dos quatro ramos veio a oferta/prazo — existe especificamente pra `notifier.py` mostrar essa origem na mensagem do Telegram, já que "IA sugeriu" e "baseado na média de propostas concorrentes" têm níveis de confiança bem diferentes na hora de aprovar. **Desconto competitivo sobre a sugestão da IA** (`_aplicar_desconto_competitivo`, 2026-09-17): confirmado em produção que a IA tende a sugerir um preço de mercado "real" bem acima do que costuma ganhar no 99Freelas (duas propostas reais saíram ~2x o valor que se mostrou competitivo) — por experiência do usuário no site, cliente geralmente fecha com o freelancer mais barato. Paliativo aplicado só no ramo `origem == "ia"`: arredonda a sugestão pra baixo no milhar mais próximo e desconta mais `proposal.ia_desconto_milhar` reais (`config.yaml`, default 1000 — ex: sugestão R$2400 → oferta R$1000; R$3300 → R$2000), nunca abaixo de `proposal.ia_preco_minimo` (default 150), e não mexe em sugestões < R$1000 (já consideradas baixas). Ainda não validado com dados reais — os dois parâmetros existem especificamente pra serem ajustados conforme o resultado das próximas propostas aprovadas. Quando o desconto muda o valor, o dict retornado ganha `oferta_sugerida_ia` (valor bruto da IA, antes do desconto) — `notifier._origem_line` mostra os dois lado a lado na mensagem do Telegram pra facilitar essa calibração.
- `ai_writer.py` — duas funções que chamam IA (Anthropic ou Gemini, configurável em `proposal.ia_provider`/`ia_model`, provider genérico `_generate_with_anthropic`/`_generate_with_gemini` aceita um `system_prompt` diferente pra cada uso): `generate_proposal_text` gera o texto da proposta a partir da descrição completa do projeto — regras (sem contato/valor/prazo, sem jargão técnico/nomes de tecnologia — cliente é leigo) reforçadas em dois níveis: instrução no prompt E `check_text_safety` (função pública — não é mais `_safety_violation` — porque `proposal.py` também usa ela, ver nota abaixo; regex de e-mail/URL/telefone/"R$"/tamanho máximo). `suggest_price_and_deadline` pede um valor/prazo em JSON estrito (`{"oferta": ..., "prazo_dias": ...}`, parseado com `json.loads` em try/except — mesma filosofia de nunca confiar só no modelo, agora validação de schema+faixa de sanidade ampla em vez de regex) quando não há dado de preço concorrente — ver `proposal.py`.
- `notifier.py` — todas as funções via Telegram (`TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` no `.env`), todas falhando sempre silenciosamente (só loga warning — notificação nunca pode derrubar o ciclo do bot): `notify_proposal_result(project, proposal, status, detail)` manda uma msg a cada tentativa de envio (sucesso ou falha), chamada de dentro de `submitter._finish` (não é chamada para projetos ignorados pelo filtro — ruído demais). Inclui a linha "Hoje: X/Y" (`_propostas_hoje_line`, ritmo diário local — `storage.proposals_sent_today()` sobre `utils.daily_quota()`) e "Conexões usadas: X/Y" (`_conexoes_usadas_line`, saldo real do site, montado a partir do cache de `connections.py` — `plano_total + nao_expiraveis` como total, `plano_total - plano_restantes` somado ao delta de `storage.proposals_sent_today()` desde o último refresh como usadas) — ambas somam +1 na proposta atual quando o envio foi real e bem-sucedido, ver nota "Contador 'Conexões usadas...'" abaixo sobre por quê. `notify_bot_status(event, detail, simulated)` é o monitoramento de **ciclo de vida** do bot (online/offline/erro), chamada de `main.py`/`dry_run.py` — por design, só dispara em transições de estado (`started`, `stopped`, `stopped_error`, `auth_failed`, `cycle_error`, `cycle_recovered`); rodando normal, sem problema nenhum, não gera nenhuma mensagem. `simulated=True` (usado por `dry_run.py`) prefixa `[DRY RUN]` pra nunca confundir com o status do bot real. Tanto `notify_proposal_result` quanto a mensagem de aprovação (`_approval_text`, ver abaixo) incluem a linha "Origem do valor/prazo" (`_origem_line`, lida de `proposal["origem_valor"]`/`ORIGEM_LABELS` em `proposal.py`) — omitida (não quebra) se a proposta não tiver esse campo (propostas pendentes antigas, montadas antes dessa mudança, já persistidas em `data/pending_approvals.json`). Se o usuário ajustar oferta/prazo pelos botões ➖/➕ (ver `_handle_adjust` abaixo), a linha ganha o sufixo "· ajustado manualmente", já que a origem original deixa de refletir o valor exibido.
  **Fluxo de aprovação**: `send_approval_request(project, proposal)` manda a proposta completa (descrição, texto, oferta, prazo — sem truncar o texto da proposta, truncando só a descrição se precisar caber no limite de 4096 chars do Telegram) com teclado inline gerado por `_approval_keyboard(project_id)`: uma linha de ajuste de oferta (➖/➕ `APPROVAL_OFERTA_STEP_REAIS`), uma de prazo (➖/➕ `APPROVAL_PRAZO_STEP_DIAS`) e a linha final "✅ Aprovar"/"❌ Rejeitar" (`callback_data` = `"approve:<project_id>"`/`"reject:<project_id>"`, limite de 64 bytes do Telegram — só o id cabe); retorna o `message_id`. `poll_decisions()` faz **short-poll** (`getUpdates` com `timeout=0` — nunca o long-poll nativo do Telegram, que bloquearia a única thread do bot), com `offset` persistido em `data/telegram_offset.json` pra nunca reprocessar o mesmo clique entre reinícios. Um clique de ajuste (`callback_data` = `"adj:<o|p>:<+|->:<project_id>"`) vai pra `_handle_adjust`, que só aplica se `approvals.get_pending` mostrar a entrada ainda sem decisão (`approvals.update_proposal` recusa — decisão tem prioridade sobre ajuste tardio) — soma/subtrai o passo (oferta com piso 0, prazo com piso 1 dia), grava com `approvals.update_proposal` e **edita o TEXTO da mensagem original** (`editMessageText`, reconstruído por `_approval_text`) pra mostrar o valor atualizado, mantendo o mesmo teclado. Um clique de decisão (`approve`/`reject`) vai pro caminho antigo: `_handle_callback` grava a decisão em `approvals.record_decision(...)` IMEDIATAMENTE (antes de qualquer coisa no Playwright — segurança contra crash, ver `approvals.py`) e troca o teclado da mensagem original por "⏳ Processando..." (evita duplo-clique durante o `finalize_submission`, que pode levar alguns segundos — e também bloqueia ajustes tardios, já sem decisão pendente pra editar). `finalize_approval_message(message_id, approved, detail)` troca o teclado de novo pro rótulo final ("✅ Aprovada e enviada"/"❌ Rejeitada") — **nunca edita o texto da mensagem** nesse ponto (diferente do ajuste, aqui já há uma decisão final e a descrição/proposta completas precisam ficar visíveis no histórico do chat como registro), só o teclado (`editMessageReplyMarkup`).
- `connections.py` — `refresh(page)` navega pra `site_selectors.DASHBOARD_URL` e extrai por regex (no `inner_text()` da página, não há seletor CSS único e estável nesse bloco) o saldo real de conexões: `plano_restantes`/`plano_total` (ex: "240 conexões restantes de um total de 240"), `disponiveis`, `nao_expiraveis` e a data de renovação. Salva em `data/connections.json` (mesmo padrão de escrita atômica de `storage.py`), junto com `baseline_sent_today` (snapshot de `storage.proposals_sent_today()` no momento do refresh). Chamado uma vez por ciclo em `main.run_cycle`/`dry_run.run_cycle`, nunca a cada proposta — `notifier.py` lê o cache (`read_cached()`) sem precisar de acesso à `Page`. Se o parse falhar ou a navegação der erro, loga warning e devolve o último cache válido (nunca derruba o ciclo).
- `submitter.py` — login por email/senha (fallback, ver `main.py` — confirmado que falha por causa do Turnstile, ver abaixo). Envio de proposta dividido em duas fases (necessário pro fluxo de aprovação: a proposta é montada no momento do match, mas o clique final só acontece depois de uma espera indefinida pela aprovação — não dá pra segurar uma aba do navegador aberta o tempo todo):
  - `prepare_proposal(page, project, config) -> (proposal | None, motivo)` — checa "já enviado" (por presença, nunca clique — ver nota abaixo), lê a descrição completa da página do projeto, checa `PROPOSAL_PREMIUM_REQUIRED_MARKER`, clica "Enviar proposta" (navega pra `/project/bid/...`, precisa `expect_navigation`), lê o valor médio das propostas concorrentes (`_read_lowest_bid`, ver nota abaixo), monta a proposta com `proposal.build_proposal`. **Não preenche nem envia nada.**
  - `finalize_submission(page, project, proposal, dry_run=False) -> (bool, detail)` — envia de fato uma proposta JÁ MONTADA (pode ter sido montada há muito tempo, dado a espera indefinida por aprovação): RE-navega e RE-checa já-enviado/Premium do zero (defensivo — o estado pode ter mudado), preenche os campos com o `proposal` recebido (sem remontar) e confirma o envio (`expect_navigation` de novo). Se `dry_run=True`, preenche mas não clica no botão final — usado por `bot/dry_run.py`.
  - `submit_proposal(page, project, config, dry_run=False)` — wrapper fino: `prepare_proposal` seguido de `finalize_submission`. É o que `dry_run.py` chama; o bot real (`main.py`) usa as duas metades separadamente, com o portão de aprovação do Telegram entre elas.
  Todo retorno de `finalize_submission` passa por `_finish()`, que dispara `notifier.notify_proposal_result` antes de retornar — se adicionar um novo caminho de saída nela, usar `_finish()` também, não `return` direto. `prepare_proposal` NÃO chama `_finish()` (não é uma notificação de resultado final) — `main.run_cycle` notifica diretamente quando o preparo falha.
- `storage.py` — persiste os IDs de projetos já candidatados e a contagem diária de envios em `data/applied_jobs.json`, usando escrita atômica (`os.replace` a partir de um `.tmp`) e um lock de thread. É isso que evita candidaturas duplicadas entre reinícios e garante a cota diária. `status` inclui `"sent"` | `"failed"` | `"skipped_duplicate"` | `"pending_approval"` (aguardando decisão no Telegram — já conta como "candidatado" pra `already_applied`, então não é reavaliado de novo enquanto espera) | `"rejected_by_user"`.
- `site_selectors.py` — **todos** os seletores CSS/XPath usados em qualquer parte do bot ficam aqui, e só aqui. Quando o HTML do site mudar ou um seletor precisar de ajuste, este é o único arquivo a mexer. **Não renomeie de volta para `selectors.py`** — esse nome colide com o módulo `selectors` da stdlib do Python e quebra o `asyncio`/`subprocess` (usado pelo Playwright) quando o script é rodado como `python bot/algo.py`, porque o Python coloca a pasta do script no início do `sys.path`.
- `utils.py` — `parse_currency`/`format_currency_br` (conversão R$ ↔ float, compartilhadas entre `scraper.py`, `submitter.py` e `proposal.py`), `minutes_since_epoch_ms`/`parse_relative_time_minutes` (idade do projeto a partir do atributo `cp-datetime` ou, em fallback, do texto "há X minutos/horas"), `daily_quota(monthly_quota)` (divide a cota mensal pelos dias do mês corrente — vive aqui, não em `main.py`, especificamente pra `notifier.py` poder importar sem criar ciclo de import, já que `main.py` importa `notifier.py`).
- `logger_setup.py` — `get_logger(name)` retorna um logger que escreve tanto no console quanto num arquivo rotativo (`logs/bot.log`).

Fluxo de dados: `run_cycle` (loop externo, ritmo `CHECK_INTERVAL_*`) faz scraping da listagem → ignora IDs já candidatados (inclui `"pending_approval"`) → para cada projeto novo, roda `filter.is_match` → se aderente, `submitter.prepare_proposal` (monta a proposta, sem enviar nada) → em sucesso, `notifier.send_approval_request` + `approvals.add_pending` + `storage.register_application(..., "pending_approval")`; em falha de preparo, notifica e registra `"failed"` direto, sem passar pelo Telegram. Separadamente, `process_pending_approvals` (loop interno, ritmo `APPROVAL_POLL_INTERVAL_SECONDS`, bem mais frequente) resolve o que `notifier.poll_decisions()` decidiu: `"approved"` → `submitter.finalize_submission` (envia de verdade) → `storage.register_application(..., "sent"/"failed")`; `"rejected"` → `storage.register_application(..., "rejected_by_user")`, sem tocar o Playwright. Em ambos os casos, todos os resultados são registrados (nada fica retentado infinitamente).

## Contexto importante para mudanças

- **Seletores de login, listagem e formulário de proposta já foram validados** contra HTML real — não são mais chutes. A lista completa de campos validados vive só em `bot/site_selectors.py` (não duplicar aqui; ela tem comentários explicando cada um). `PROPOSAL_LOWEST_BID` está validado, mas lê o **"Valor médio das propostas"** (`.generic.information`, parseado por regex em `submitter._read_lowest_bid`), não o menor valor de verdade — essa distinção real não está disponível sem Premium. Confirmado: esse bloco só existe em projetos com propostas suficientes acumuladas pra calcular a média; em projetos recém-publicados (o alvo do `max_project_age_minutes`) costuma estar ausente — reforça ainda mais a importância de um `oferta_fixa` de segurança no `config.yaml`. **Ainda pendente**: onde fica o orçamento do cliente na página do projeto — bloqueado pelo plano Premium inativo (ver nota abaixo sobre `PROPOSAL_PREMIUM_REQUIRED_MARKER`).
- **Confirmado (2026-09-17, testado em 10/10 projetos reais da listagem): sem o plano Freelancer Premium ativo, NENHUM projeto mostra o botão "Enviar proposta"** — aparece um link "Ver plano" (`/freelancer-premium`, seletor `PROPOSAL_PREMIUM_REQUIRED_MARKER`) no lugar, mesmo com conexões disponíveis ("Conexões disponíveis" no dashboard não é suficiente; é uma restrição de plano separada). `submitter.submit_proposal` checa esse marcador ANTES de tentar clicar em `PROPOSAL_BUTTON` e retorna cedo com detalhe claro, em vez de bater timeout de 8s e reportar o genérico "botão não encontrado (projeto pode ter fechado)". Até o plano ser ativado, espere que `dry_run.py`/`main.py` só consigam simular/enviar propostas de fato depois disso — não é bug do bot, é o site cortando o acesso.
- **Descoberta ainda não aproveitada**: valores individuais de propostas de outros freelancers (ex: "Enviei uma proposta de R$ 125,00...") aparecem no texto acessível (`inner_text()`) da página do PROJETO (não a de envio) MESMO em projetos bloqueados por `PROPOSAL_PREMIUM_REQUIRED_MARKER` — diferente do "Valor médio das propostas" (que é na página de envio e já está implementado, ver acima). Poderia dar acesso a uma "menor proposta" de verdade mesmo sem Premium, mas ainda não foi implementado — precisa validar a estrutura exata desses elementos (`text=/Enviei uma proposta/i`) antes de usar.
- **Bug real corrigido**: o marcador de "proposta já enviada" inclui `#btnCancelarProposta` (um link que CANCELA a proposta se clicado). O código original usava `page.click()` pra checar esse marcador — clicar nele cancelaria propostas já enviadas. Corrigido pra `page.query_selector()` (checagem de presença, nunca clique). Se algum dia reintroduzir uma checagem "existe X na página", pensar sempre se o elemento é seguro de interagir antes de usar `.click()` como forma de "testar presença".
- **"Enviar proposta" e o botão de confirmar envio são navegações de página real** (`/project/bid/...` e volta pra página do projeto), não revelam formulário/toast na mesma página — por isso ambos os cliques em `submitter.py` usam `page.expect_navigation(wait_until="networkidle")`. Se replicar esse padrão de clique+espera em outro lugar, não esquecer o `expect_navigation`.
- **O campo de oferta (`#oferta`) espera formato brasileiro** (`"1234,56"`, vírgula decimal, `type="tel"` com máscara) — sempre usar `utils.format_currency_br()` ao preencher, nunca `str(float)` puro (isso já foi um bug real, corrigido).
- **A listagem de projetos não mostra orçamento** — confirmado no HTML real (só categoria, nível, data, descrição, contagem de propostas/interessados, cliente). `project["budget"]` vem sempre `None` do `scraper.py`. Isso importa para `proposal.py`: sem orçamento do cliente e sem valor médio de propostas concorrentes (comum em projetos recém-publicados), `build_proposal` pede à IA uma sugestão de preço em vez de cair pra `oferta_fixa`/0 — ver `ai_writer.suggest_price_and_deadline` e o bullet de `proposal.py` acima.
- **`oferta_fixa` deixou de ser pré-requisito obrigatório de segurança** (era: "nunca ativar em produção sem `oferta_fixa` preenchido, senão pode enviar R$0,00"). Isso mudou porque agora **toda proposta real passa por aprovação humana no Telegram antes de ser enviada** (ver `approvals.py`/`notifier.py`/`main.process_pending_approvals`) — um valor ruim ou ausente simplesmente não vira um pedido de aprovação (`build_proposal` retorna `None`, `prepare_proposal` trata como falha de preparo), em vez de ser enviado sozinho. `oferta_fixa` continua útil como estratégia própria (`oferta_estrategia: "fixo"`), só não é mais obrigatório configurar antes de ligar o bot.
- **Login automatizado é bloqueado por Cloudflare Turnstile**: confirmado testando as duas formas (clique automatizado no Google e preenchimento automatizado de email/senha via `submitter.login`, seletores já validados: `#email`, `#senha`, `#btnEfetuarLogin`) — o Turnstile no formulário rejeita ambas com "token de acesso inválido" por detectar automação. Não tentar contornar isso (stealth plugins, resolvedores de captcha etc.) — é a proteção do próprio site funcionando como esperado. O caminho funcional é `import_cookies.py` (cookies exportados do navegador comum do usuário, já logado). `data/auth_state.json` gerado por ele é reaproveitado por `main.py` via `open_authenticated_page`. `submitter.login` (email/senha) só roda como fallback se esse arquivo não existir, mas está confirmado que vai falhar por causa do Turnstile. Quando a sessão salva expira, o bot loga um erro e para — é esperado que o usuário refaça a importação de cookies, não algo pra "corrigir" automaticamente.
- **`config.yaml`, `.env` e `data/auth_state.json` são gitignored e específicos do usuário/sessão**; só os `.example` ficam commitados. Nunca commite credenciais reais, cookies de sessão ou um `config.yaml` preenchido.
- **Cota de propostas**: `MONTHLY_PROPOSAL_QUOTA` no `.env` (240, correspondente às conexões do plano do usuário) é dividido pelos dias do mês corrente em `utils.daily_quota()`, recalculado a cada ciclo — não é um número fixo por dia. Isso, junto com os delays aleatórios entre ciclos/propostas (`CHECK_INTERVAL_MIN/MAX_SECONDS`, além do sleep de 5–15s entre propostas dentro de um mesmo ciclo), existe especificamente para não gastar a cota mensal de uma vez e evitar parecer spam para a plataforma — preserve esse comportamento ao refatorar o loop de ciclos. A notificação Telegram mostra esse ritmo diário na linha "Hoje: X/Y" (`notifier._propostas_hoje_line`, X = `storage.proposals_sent_today()`, Y = `utils.daily_quota(monthly_quota)`), separada da linha "Conexões usadas" (ver abaixo) — uma é o ritmo local que o bot se impõe, a outra é o saldo real do site.
- **Conexões do plano**: cada proposta enviada consome uma "conexão" do plano 99Freelas do usuário (visível no dashboard em "Minhas conexões"). O plano Gratuito dá só ~10/mês; o valor de `MONTHLY_PROPOSAL_QUOTA=240` no `.env` assume que o usuário está num plano pago com 240 conexões/mês — se o plano mudar, esse valor precisa ser atualizado junto, senão o bot vai tentar enviar mais propostas do que há conexões disponíveis e as excedentes vão falhar.
- **Contador "Conexões usadas: X/Y" na notificação Telegram usa o saldo REAL do `/dashboard` (`connections.py`), não `MONTHLY_PROPOSAL_QUOTA`/`utils.daily_quota()`** — decisão deliberada, confirmada com o usuário: a renovação real do plano não necessariamente cai no dia 1 do mês (ex: conta real com renovação em 17/10/2026), e pode haver conexões não-expiráveis somadas ao total, então dividir a cota mensal por dias do calendário (o que `daily_quota()` ainda faz, só pra ritmo de envio, numa linha separada "Hoje: X/Y" — ver bullet de "Cota de propostas" acima) daria um número errado pro contador exibido. `connections.refresh(page)` só roda 1x por ciclo (não a cada proposta) pra não multiplicar navegações; por isso `notifier._conexoes_usadas_line` soma localmente (via `storage.proposals_sent_today()`) o que foi enviado depois do último refresh, incluindo +1 pra proposta que está sendo notificada agora (a notificação dispara ANTES do `storage.register_application` correspondente, dentro de `submitter._finish`). Se o parser de `connections.py` quebrar (mudança de layout do dashboard), a notificação simplesmente omite essa linha (retorna `None`) em vez de quebrar o ciclo.
- **Bug real corrigido no denominador do contador de conexões**: `_conexoes_usadas_line` usava só `plano_total` como Y (ex: "0/240"), mas numa conta real com 6 conexões não-expiráveis, o saldo total de verdade é maior (240 + 6 = 246, igual ao "Conexões disponíveis" do dashboard) — usar só `plano_total` faria o contador passar de Y antes de esgotar o saldo real. Corrigido pra `Y = plano_total + nao_expiraveis`. O numerador (`usadas`) não mudou — é sempre `plano_total - plano_restantes` + o delta local desde o refresh, porque `nao_expiraveis` se cancela na subtração (só afeta o total exibido, não o quanto já foi usado).
- **Modelos "thinking" do Gemini (ex: `gemini-3.6-flash`) consomem `max_output_tokens` com raciocínio interno antes do texto final** — sem `thinking_config=ThinkingConfig(thinking_budget=0)` em `ai_writer._generate_with_gemini`, o texto sai cortado na metade (confirmado testando: `thoughts_token_count` alto, resposta truncada). Não remover esse `thinking_budget=0` sem motivo forte.
- **Chaves de API vazam e são detectadas**: já aconteceu nessa sessão — o Google rejeitou uma `GEMINI_API_KEY` com "Your API key was reported as leaked" mesmo sem ela nunca ter sido commitada (`.env` é gitignored). - **Bug real corrigido em `is_logged_in()`**: usava `page.wait_for_selector(..., timeout=3000)` sem especificar `state`, que por padrão exige o elemento **visível**. O seletor `a[href^='/user/']` provavelmente bate primeiro com uma versão escondida (menu mobile/responsivo) antes da visível, fazendo a checagem falhar (timeout) mesmo com sessão 100% válida — reproduzido de forma consistente (`query_selector` achava o elemento, `wait_for_selector` não). Se `is_logged_in()` voltar a reportar falso negativo, suspeitar de visibilidade/duplicação do seletor antes de assumir que a sessão expirou.

- **Bug real de produção corrigido: o template fixo de `proposal.texto` em `config.yaml` incluía `{oferta}`/`{prazo_dias}` no corpo do texto** ("Minha oferta é de R$ {oferta}, com prazo estimado de {prazo_dias} dias corridos").
